# ADR 0039 — Three-way derived-features ablation on the forecaster head

Issue #309 ships the methodology rewrite of the derived-text-features ablation as a three-arm sweep on the canonical fold protocol. The §16 walkthrough surfaces a structural concern about the forecaster head: it reads BOTH a rich 128-dim document-level embedding (the encoder over the full text) AND five derived-feature columns produced by per-sentence inference plus majority-vote / mean aggregators. The two paths plausibly carry overlapping signal — the encoder already aggregates the per-sentence axes via chunked attention over the full document, and the per-sentence multi-axis classifier sits at macro-F1 ≈ 0.50 – 0.55 per axis, so roughly half its labels are wrong before the aggregator collapses them. The hypothesis the ablation tests is that the derived-feature path is either a degraded copy of the encoder signal (redundant) or actively noisy (the per-sentence error rate plus the argmax-destroys-confidence collapse), and the right call is to remove the path from the forecaster's input space.

The five columns the §16 walkthrough names — ``sentiment_score`` / ``stance_label`` / ``factor_labels`` / ``certainty_score`` / ``topic_label`` — are precisely the surface this ablation isolates. The broader per-family ablation under #334 / PR #371 zeros each rich-feature family one at a time (linguistic, mp_surprise, multi_axis, llm_features, realised_vol, cross_asset, credibility) on the same canonical surface; #309's question is narrower and overlaps the per-family runner's ``multi_axis`` cell partially. The clean separation is that #334 owns the per-family question (which family carries the most lift) and #309 owns the specific question the issue body asks (do these five columns specifically belong in the forecaster input). The two answers can disagree without contradiction — the per-family cell aggregates the answer over a wider slot range than the five-column slice.

## The three arms

``baseline`` is the canonical pipeline byte-identical to the pre-#309 head. ``ModelConfig.use_derived_text_features=True`` and no FeatureVector slot is touched before the per-fold scaler fit. The cell reads the same input tensor the canonical sweep has emitted since #173 widened the rich-feature payload. ``derived_ablation`` flips ``use_derived_text_features=False`` and walks every loaded sequence to zero five FeatureVector slots in place: ``sentiment_score`` at per-bar position [0], the stance one-hot at positions [29:32] (``stance_hawk`` / ``stance_dove`` / ``stance_neutral``), and ``certain_label_certain`` at position [33]. ``factor_labels`` and ``topic_label`` have no per-bar slot — they ride the multi-task auxiliary loss path — and the matching mask collapse runs inside ``train_model``'s ``_zero_derived_text_features`` helper, gated on the same ``use_derived_text_features=False`` flag, so the auxiliary loss contribution from each axis drops to zero alongside the per-bar zeroing. ``derived_replacement`` applies the same narrow zero plus the #291 pre-meeting rates columns into the slots the zero clears; the loader piece is tracked under #315 and the arm currently emits the same input tensor as ``derived_ablation`` with a deferral status on the manifest.

The five-column zero is applied BEFORE the per-fold RobustScaler is fit. That ordering is the load-bearing piece: the scaler sees the zero column on the train slice and locks the median + IQR at the no-signal state, then applies the same transform to val + test so the post-scale value stays a literal 0 across the partition. The pattern mirrors PR #371's per-family ablation (``_zero_per_bar_market_aux``) and the original #309 ``_zero_derived_text_features`` contract from PR #314. ``stance_missing`` (slot [34]) is intentionally NOT zeroed — it's a missingness flag, not a derived signal, and flipping it would leak a "stance unknown" signal the baseline arm does not see either.

## The decision criteria

The three-arm comparison drives three downstream calls and the §16 narrative carries the diagnostic into one of three readings:

*The derived features hurt or are neutral.* The ``derived_ablation`` cell matches or beats baseline on regime macro-F1 inside the bootstrap CI band. The reading is that the encoder already captures the multi-axis signal — the multi-task null result under PR #282 (#273 joint training did not lift downstream macro-F1) is circumstantial evidence in this direction. Follow-ups #310 and #315 close as won't-fix; the forecaster head's input space is decoupled from the derived columns in a separate PR; Panel 1 keeps surfacing the derived features as a presentation surface unchanged, because the user-facing decision support is a different question from the forecaster input. This is the publishable null result the issue body anticipates: "we tested whether sentence-level derived features add forecaster-relevant signal over the document-level encoder path, and found no measurable lift" is a clean methodology finding.

*The derived features lift baseline.* ``derived_ablation`` is materially worse than baseline (outside the bootstrap CI band). The reading is that the five columns carry signal the encoder does not pick up — the per-sentence aggregation is a legitimate parallel path. #310 ships the implementation improvements (softmax distributions instead of argmax labels, sentiment-model swap to FOMC-domain weights or the internal stance head, salience-weighted aggregation that decays from start to end of document or rides per-sentence attention) and the methodology contribution becomes the per-feature implementation choice rather than the architectural inclusion choice.

*The derived features are noise but the encoder catches it anyway.* ``derived_ablation`` matches baseline but ``derived_replacement`` (once #315 wires the pre-meeting rates columns) lifts above both. The reading is that the slots the five columns occupy carry capacity-allocated input space the model uses, but the actual signal the head reads is whatever is in those slots — derived columns or pre-meeting rates. #315 ships the pre-meeting wiring; the forecaster's input space stays at the same RICH_FEATURE_SIZE width; the §6 table reads the rates-pre-meeting substitution as a positive ablation. This reading is the most consequential because it justifies a feature-space surgery the other two readings do not.

## What ships now, what's GPU-blocked

The runner-side code lands here — the narrow zero helper at ``scripts/run_derived_features_ablation.py::_zero_five_derived_columns_inplace``, the ``--arm`` CLI flag with the three-arm vocabulary (``baseline`` / ``derived_ablation`` / ``derived_replacement``) and the legacy ``ablation`` / ``replacement`` aliases that resolve to the new names so the PR #314 CLI surface keeps working, the manifest fields (``arm`` / ``five_derived_columns`` / ``five_derived_fv_attrs`` / ``five_derived_mt_aux_axes``) so the §16 row can read which arm and which slot set the cell exercised, and ``summary.<arm>.regime_f1_macro.{mean, std, lo, hi, n}`` so the table can carry both the across-observation std and the block-bootstrap CI. The unit tests at ``tests/unit/test_derived_features_ablation.py`` pin the arm vocab, the legacy-alias resolution, the CLI flag dispatch, the five-column FeatureVector attribute list, the in-place zero contract on the per-bar slots, the as_rich_list shape preservation under the zero, and the baseline byte-identical contract.

The five-seed × walk-forward × N-epoch sweep that populates ``backend/artifacts/experiments/derived_features_ablation.json`` with the actual per-arm numbers is GPU-blocked behind the canonical sweep return. The harness code lands; the answer to "do the five derived columns help" lands when the Runpod sweep runs. The methodology contract is the artefact this PR ships — the experimental answer is one command away once the queue clears.

## What stays out

The implementation-side improvements #310 lists (softmax distributions instead of argmax labels, sentiment-model swap, salience-weighted aggregation) are conditional on this ablation's outcome and ship under #310 if the ablation justifies them. The pre-meeting wiring #315 owns is a separate loader refactor that injects the 12 #291 pre-meeting rates columns into the FeatureVector slots the narrow zero clears; until that lands the replacement arm emits the same input tensor as the ablation arm and the runner records the deferral status on the manifest. The Panel 1 presentation surface stays unchanged regardless of which reading the ablation produces — the user-facing decision support is a separate question from the forecaster head's input space, and the issue body draws that line explicitly.
